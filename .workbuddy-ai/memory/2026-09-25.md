### What Phase 4.1 delivered

  break the generated Java.
- **`navigation/RoutingConfig.java`** (NEW) — the ONLY reader of `BuildConfig.ORS_API_KEY`.

  `MapMarkerController.markerIconRes` and `DateTimeHelper`'s injected zone/locale).
- `local.properties` was temporarily given a placeholder key and then **restored exactly**.

### VERIFIED against the LIVE API (no key needed) — the most valuable output of the phase
- `POST https://api.openrouteservice.org/v2/directions/driving-car/geojson`
  - no `Authorization` header → **HTTP 401** `{"error":"Authorization field missing"}`
  - bogus key → **HTTP 403** `{"error":"Access to this API has been disallowed"}`
- So: **the endpoint path is right** (a wrong path gives 404), **the key goes in the `Authorization`
  HEADER, not `?api_key=`** (older ORS versions used the query param; most online examples still show it),
  and **403 means bad key while 401 means missing key** — 4.2 can tell those apart for the user.
- **GeoJSON coordinates are `[longitude, latitude]`** — the reverse of how coordinates are spoken.
  Getting it backwards silently puts every route in the sea off the coast of Africa.

### Verified by building (not assumed)
- App **builds, tests and packages with NO key** → `BuildConfig.ORS_API_KEY = ""`.
- Placeholder key → incremental build → `BuildConfig.ORS_API_KEY = "VERIFY_PLACEHOLDER_NOT_A_REAL_KEY"`.
- Line removed → incremental build → back to `""`. **So an incremental build DOES pick up a changed key**
  (worth checking, because `buildConfigField` is a compile-time constant and javac inlines it).
- `grep -rn "VERIFY_PLACEHOLDER" app/src/` → **no matches**. The key never enters the source tree.
- APK searched dex by dex → **0 occurrences**. `ORS_API_KEY` does not even survive as a symbol (inlined).
- **144 tests, 0 failures.** Schema still only `1.json`. Permissions unchanged. Still zero Kotlin.

### Trap worth keeping
- **A `buildConfigField` is baked into the APK** and extractable from it. Fine for a solo app (D-5), but
  **the debug APK must never be shared**. Also: after changing the key, a clean build removes all doubt.

### Decisions recorded FOR 4.2 (in the phase doc §13.7)
- HTTP client: **`HttpURLConnection`** (in the platform, zero deps). JSON: Android's built-in **`org.json`**.
- **One test-only dependency will be needed: `testImplementation 'org.json:json:…'`** — the platform's
  `org.json` is a JVM stub that throws "not mocked", so without a real copy the parser cannot be unit-tested.
- Nothing calls `RoutingConfig` yet — 4.2 is its first caller.

### Architecture decision worth remembering
- **The route lives as `LiveData` on the repository**, not handed between fragments. The sheet that ASKS
  for a route and the Map tab that DRAWS it cannot see each other, and this avoids re-adding the
  fragment-result plumbing Phase 3.4 deliberately removed. Same shape as `LocationProvider.currentFix()`.
- **Only `READY` draws a line; every other status clears it** — otherwise a failed request leaves the
  PREVIOUS route on the map, presented as the answer to the request just made.

### Three traps (all now in HANDOFF §8)
1. **`[longitude, latitude]` — in BOTH directions.** The request body AND the response. A swap is not an
   error: it is a valid request for the wrong place, and the service answers with a valid route to it.
   `RoutingRepository.coordinatePair` sends it; `RouteResponseParser.parsePoints` reads it back.
   Tested with a NEGATIVE longitude, because a "bigger number = longitude" shortcut looks correct in the
   Philippines and is wrong everywhere in the Americas.
2. **The `<queries>` manifest element.** Without it `resolveActivity()` returns null on Android 11+ even
   with Google Maps installed → Start navigation does nothing, with no exception and no log.
3. **`String.format` uses the device locale.** `%.6f` of 14.5995 on a German phone gives `14,599500`, which
   the URI reads as TWO values. Both formatters pin `Locale.US`, with tests that set the default locale to
   GERMANY in a try/finally to prove it. Also: `Double.toString` can give `1.0E-5` — use `%.6f`.

### Phase boundary shift (documented in the phase record §13.7)
**Start navigation + `<queries>` moved from 4.3's row into 4.2.** Reason: the screen plan's own §13.8 lists
Start Navigation as screen 7's primary button, and a preview with no way to act on it is a dead button.
**4.3 still has**: the foreground service, FOREGROUND_SERVICE + FOREGROUND_SERVICE_LOCATION +
POST_NOTIFICATIONS, the arrival notification, `sheet_navigation_active.xml`, and
`ActiveNavigationSession` in `lastSelectedStoreId`. **4.2 deliberately does NOT set `lastSelectedStoreId`** —
no monitoring service means no session to resume and nothing to clear it.

### The reason this phase exists: the 164 m trap
A Google Maps place link contains **TWO coordinate pairs**:
```
…/maps/place/Alfamart/@14.6010,120.9900,17z/data=…!3d14.599528!4d120.984206…
                    └─ the CAMERA ─┘            └─── the PLACE ───┘
```
Measured **164 m apart**. The app's arrival radius defaults to **50 m**. Reading the `@` pair (the obvious
one, and what most examples online use) pins the store on the wrong side of the building → the app
**never offers to complete that store and never says why**. Two tests hold the right order; one is a pure
regression guard. **This is the single most important thing in the phase.**

### What was built (22 files: 9 new, 12 modified, 1 deleted/renamed)
- `domain/GoogleMapsLinkParser` — PURE, **28 tests**. Precedence: bare `lat,lng` → `geo:` → `!3d`/`!4d` →
  `?q=`/`query=`/`ll=`/`daddr=` → `@`. The bare pattern is **anchored** so it cannot match numbers inside a
  URL; the cost (`"Location: 14.5, 120.9"` is not read) is a documented test, not a surprise.
- `domain/PlaceLinkState` — status + coordinate in ONE object (mirrors `RouteState`).
- `data/repository/PlaceLinkRepository` — `LiveData<PlaceLinkState>`. Full link = **no network**; short link

- Map tab FAB `fab_add_from_link` + `ic_add_link`; `MapFragment.observePlaceLink()` **centres the camera**.
