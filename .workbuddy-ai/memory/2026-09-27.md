### Traps learned this phase (also in HANDOFF §8 / the skill)
- **`@Transaction` covers ONE DAO only.** An operation spanning two tables must live in a single DAO or it
  is not atomic at all.
- **Throwing is what rolls a Room transaction back.** Room calls `setTransactionSuccessful()` only when the
  method returns normally — a half-applied write must throw, not return an error value.
- **A DAO does not change the schema.** Only entities do. `1.json` untouched, `DATABASE_VERSION` still 1.
- **Two `PendingIntent`s with the same request code are the SAME intent** — identity is action + data +
  component, **not** the extras. The ongoing notification is re-posted every few seconds, so a shared
  request code would wipe the arrival's store id almost immediately. Ongoing = 0, arrival = 4102.
- **Never let the transaction read the clock itself** — read it once, pass it down, or 23:59:59.999 gets
  filed under the wrong day.
- **`Locale.US` must be pinned on the `YYYY-MM-DD` pattern.** A Buddhist-calendar locale would render 2026
  as 2569; a key sorted as a string must always be the same shape.
- **A rotation mid-write loses the callback** (the write runs on an Application-owned thread). Do not save a
  result — re-read the database, the only surviving record (AD-4).

## Phase 7.0 — Rounds, Undo, and the At-Store Shortcut ✅ code complete, build verified

Requested directly by the user (not on the roadmap), numbered **7.0** so the roadmap's 7.1–7.4 keep their
numbers. It is also a **prerequisite** for them: a suggestion strategy needs to know which stores are still
to visit *in the current round*.

### ⚠️ THE FIRST SCHEMA MIGRATION IN THE PROJECT — v1 → v2

This is the headline. `AD-5` changed from `UNIQUE(storeId)` to **`UNIQUE(storeId, roundNumber)`** — a
**generalisation, not a weakening**: the guarantee was always "do not double-count", and a store still
cannot be counted twice in the same round.

`MIGRATION_1_2` (in `AppDatabase`), five statements:
```sql
ALTER TABLE completion_history ADD COLUMN roundNumber INTEGER NOT NULL DEFAULT 1;
DROP INDEX IF EXISTS index_completion_history_storeId;
CREATE UNIQUE INDEX IF NOT EXISTS index_completion_history_storeId_roundNumber
    ON completion_history (storeId, roundNumber);
CREATE INDEX IF NOT EXISTS index_completion_history_roundNumber ON completion_history (roundNumber);
ALTER TABLE app_settings ADD COLUMN currentRound INTEGER NOT NULL DEFAULT 1;
```
Registered with `.addMigrations(MIGRATION_1_2)`. **Still no `fallbackToDestructiveMigration()`** — the first
real opportunity to use it, and it was not taken.

### What was built
- `domain/RoundProgress.java` + `domain/RoundCalculator.java` (PURE, 14 tests) — the round rule.
- `data/db/RoundOutcome.java` + `data/db/RoundTransactionDao.java` — **`startNewRound()`**, the only thing
  that resets a store's status. Re-checks completeness **inside** the transaction; **throws** to roll back.
- `CompletionTransactionDao` — round-scoped guards + insert, and **`undo()`**: one named row, by row id,
  resets the store only when the row belonged to the current round.
- `TrackerCalculator` / `TrackerSnapshot` — round-aware. **"Remaining" and "Completion" changed MEANING**
  to round-scoped (a lifetime figure cannot go back up); "Overall completed" stays lifetime.
- `ConsistencyChecker` — round-scoped, or it would report the whole route as inconsistent the moment round
  2 began.
- `StoreDetailBottomSheet` — **at the store, "Get directions" is replaced by "Store completed?"**, which
  opens the same dialog. The decision is `ArrivalEvaluator`'s, not the sheet's.
- Dashboard round cards + a round-complete message; Settings round panel with Start next round.
- `CompletionDetailFragment` now takes a **history row id** (not a store id) — with rounds a store has one
  row per round.

### ADRs added: AD-27 … AD-31
- **AD-27** One round = one complete pass of every store. Starting a new round deletes nothing.
- **AD-28** A round is complete when every store *currently in the database* has a completion in it — so a
  store added mid-round re-opens the round.
- **AD-29** `currentRound` is **stored**, not derived from `MAX(roundNumber)` — a fresh round has no rows.
- **AD-30** The undo removes exactly one named row and is the only destructive operation on the table.
- **AD-31** Dashboard "Remaining"/"Completion" are round-scoped; "Overall completed" is lifetime.

### Traps learned (also in HANDOFF §8 / the skill)
- **`ADD COLUMN` on a table with rows needs a `DEFAULT`** — it is the only form SQLite allows without
  rewriting the table. Both v2 columns carry one, and for existing rows the default is the true value.
- **A migration must be REGISTERED.** Writing it and forgetting `.addMigrations(...)` is a crash at launch.
- **An index name in a migration must be Room's own** — read it out of the exported JSON, do not guess.
- **A changed unique index changes the ENTITY too.** The migration and `@Entity(indices = ...)` must agree
  or Room's schema validation fails at open.
- **`./gradlew` exporting `2.json` proves the ENTITY, not the migration.** They are two different artefacts
  that must produce the same shape.

## Version 11 — Glassmorphism UI + three LiveData bugs fixed ✅ build verified

Asked for as "pa fix kung may problem at gawing modern glassmorphism ang ui design ng buong app".

### The bugs (found by auditing every `LiveData.getValue()` in the app)

**All three are the same root cause:** `LiveData.getValue()` returns `null` until something observes it.
Reading a repository's LiveData from a screen that does not observe it *appears* to work, because another
screen usually observed it first — so it fails only in the case that is hardest to notice.

1. **`OptimizedRouteFragment.pendingStores()`** — read three repositories via `getValue()`. If the app was
   restored straight to the route screen (process death with the back stack rebuilt), all three were null
   and the screen claimed **"Nothing left to visit in this round"** when there was a full round outstanding.
   **Fixed**: three chained one-shot reads (`findAllNow` / `getNow`), and the position is now *observed* so
   `currentCoordinate()` has a value.
2. **`DashboardFragment.renderRoundComplete()`** — read the settings row via `getValue()` to decide whether
   Home was set. The first render can arrive from the **stores** source before the settings row has ever
   been delivered, in which case the round-complete card offered **"Set a Home location in Settings"** when
   Home was set all along. **Fixed**: `DashboardViewModel.hasHome()` / `homeCoordinate()`, because the
   ViewModel is the object that actually observes settings.
3. **`SettingsFragment.runConsistencyCheck()`** — same read of the settings row. **Fixed**: `getNow()`.

Audited and **left alone** because they are genuinely safe: `NavigationSession` (owns its own
`MutableLiveData`), `RoutePreviewBottomSheet` (initialised `MutableLiveData`), `DailyHistoryFragment.join`
(handles null), `MapFragment.locationEnabled` (observed).

### The glassmorphism

- **`drawable/bg_glass_gradient.xml`** — the window background: a 315° three-stop gradient plus two radial
  colour blobs. One file; the night variant comes free because it references colours that have
  `values-night` counterparts.
- **`android:windowBackground`** in the theme, so every screen gets it with no per-layout work, the launch
  window uses it, and there is no flash of a flat colour.
- **Every screen root is now `@android:color/transparent`** — this is what makes the cards translucent.
  An opaque root would cover the gradient and silently flatten the whole effect.
- **`Widget.AlphaRoute.StatCard`** — 20dp radius (was 12dp), `glass_fill` translucent background,
  `glass_stroke` 1dp rim, elevation 0 (a hard drop shadow under frosted glass looks wrong).
- **Toolbar, bottom nav, five bottom sheets and dialogs** all use the chrome treatment. Sheets are rounded
  at the **top only** — the bottom edge is off-screen and rounding it leaves visible slivers.
- New colour roles in **both** `values/colors.xml` and `values-night/colors.xml`: `glass_gradient_*`,
  `glass_blob_*` (+ `_end`), `glass_fill`, `glass_fill_strong`, `glass_fill_accent`, `glass_stroke`,
  `glass_chrome`, `glass_scrim`.
- **The blobs fade to a zero-alpha version of their own hue**, never to `@android:color/transparent` —
  that is transparent *black*, and fading blue to it passes through grey and leaves a dirty smudge.
- The accent cards (round-complete, empty state) moved from `?attr/colorSecondaryContainer` to
  `glass_fill_accent`, and their text from `colorOnSecondaryContainer` to `colorOnSurface` — the old role
  no longer describes what they are.

**No new dependency, no schema change, no permission, zero Kotlin.**

## Phase 12 — The round report ✅ build verified

Requested as: *"meron den yan dapat na makikita kung anong store natapos nung araw na yun yung date at ilang
store natapos nung araw na yun sa isang round ilang araw ang tinagal bago natapos like 65 stores per round
and 23 store on day 1"*.

### What it answers that nothing else could

The History tab shows **one day**; the Dashboard shows **the round in progress**. Neither can say *"round 2
was 65 stores over 4 days — 23 on day 1, 18 on day 2"*, because that is a question about a whole round, and
**a round is not a day**.

### Built

- **`domain/RoundDay`** — one day inside a round: `dayNumber` (1-based, **not** the day of the month),
  `dateKey`, and the store ids done that day.
- **`domain/RoundReport`** — one round: total stores, days taken, start/end date keys, `isComplete()`.
- **`domain/RoundGrouper`** — pure, 17 tests. Groups history into rounds, and each round into its days.
- **`ui/history/RoundReportFragment`** + **`RoundReportAdapter`** — a card per round, a row per day, and the
  store codes revealed when a day row is tapped.
- **History tab header card** — shows the round in progress at a glance ("65 stores · 4 days") and is the
  way into the report.
- `DateTimeHelper.shortDateTextFromKey()` — "1 Sep" without the year, for the day rows.

### Three decisions worth keeping

1. **`daysTaken` counts days WORKED, not the calendar span.** A round worked on the 1st and then the 10th is
   **two** days of work with nine days in between; "10 days" would be a misleading answer to "how long did
   it take".
2. **Rounds come back newest first; days come back oldest first.** Deliberately different orders — the round
   in progress is what the user is living in, and "day 1, day 2, day 3" is the order the story makes sense
   in.
3. **A round is complete if the user moved past it OR it covered the whole route.** The count alone gets it
   wrong for a round closed early that then had a store added (reads as open for ever); the round number
   alone gets it wrong for the round in progress, which finishes the moment its last store is done.

### Reused the AD-37 lesson

`RoundReportFragment` uses **chained one-shot reads** (`getNow` → `findAllNow` → `findAllNow`), not
`observe().getValue()`. A report is a snapshot of a moment, and a read must not depend on another screen
having observed the same LiveData first. `HistoryFragment` does the same for the header card's two numbers.

## Version 11.1 — the glassmorphism improved ✅ build verified

Asked for as "can you improve its ui?". Rather than adding things, I looked for what was actually weak.

### The main flaw: the gradient was too pale to see through

The original three stops (`#EAF0FC` / `#F1EDFA` / `#E7F1F7`) were all within a few points of white, and the
blobs sat at 20% alpha on top of them. **There was almost nothing to see through a translucent card** — so
the cards read as flat white panels with a faint tint. Glass needs contrast behind it.

- Gradient deepened: light `#D5E4FA` / `#EBDDF6` / `#D2E7F3`; dark `#0A0C12` / `#161733` / `#080F13`.
  Still light on purpose — the app is used outdoors in daylight, and a saturated backdrop would fight the
  map tiles and the numbers the driver has to read.
- Blobs raised to 30% (light) and 35% (dark).
- **A third blob, centred, at a smaller radius.** With only two corner blobs the middle of a tall screen had
  no colour in it, so a card scrolled to the middle had nothing behind it to refract — exactly the moment
  the glass stopped looking like glass.

### The bars fade instead of stopping

Two new drawables: `bg_glass_chrome_fade_up` (toolbar, dissolves at its bottom edge) and
`bg_glass_chrome_fade_down` (bottom bar, fades in at its top). Content scrolling under a hard edge reads as

## Version 13 — A completed store can now be deleted ✅ build verified

Requested as: *"pede pa ren madelete yung store kahit completed na mag lagay lang ng popup text saying are

### The change

Until now **AD-6's `onDelete = RESTRICT` made a completed store undeletable**, and the app said "This store
has completion history and cannot be deleted." That left no way at all to remove a store completed by
mistake, or one that has closed down.

### How it was done WITHOUT weakening the guarantee

**The foreign key is unchanged.** Changing `RESTRICT` to `CASCADE` would mean recreating the

change, a migration, and a rewrite of every row, for behaviour that a transaction already provides.

So: **`StoreTransactionDao.deleteWithHistory()`** deletes the history rows FIRST, then the store, in one
`@Transaction`. By the time the store row goes, nothing references it, so the constraint is satisfied and
**nothing is ever orphaned**. Every failure path throws, so a half-done delete rolls back.

**No schema change, no migration.**

The dialog now states what goes with the store, with the number:
*"R-04 will be removed from the map, and 3 completion records recorded against it will be deleted too."*

- The count is read **one-shot** at the moment the dialog is built (`CompletionRepository.countForStore`),
  so the number is current, not captured earlier.
- If the count read fails, the message warns **without** a number rather than not warning.
- The Delete button is **always enabled** now; a line under it warns before the tap, so the rule is visible
  instead of hidden behind a disabled control.

## Version 18 — Saved route plans: the DATA LAYER ✅ build verified (UI still to do)

User: *"yung plan the whole route ehh lalabas lang yung mga stores tapos pag susunod dunurin manually… pede
dapat mag save ng plan like unang plano may name default plan… minsan kase nag iiba yung plan ehh"*

**The problem is real.** The optimiser is a solver: given the same problem it can return a different order
(a different matrix, a road closure, a retrained service). So "the plan" was never a thing the app could
promise — it was whatever the last request happened to return. A saved plan is a decision the user made and
the app keeps.

### Built: the schema (v2 → v3, the SECOND migration in the project)
- **`RoutePlanEntity`** — id, name, roundNumber, createdAt, totals, startedAtLocation, endedAtHome.
- **`RoutePlanStopEntity`** — planId, storeId, position, leg distance/duration.
- **`RoutePlanDao`** — `savePlan()` and `deletePlanOrThrow()`, both `@Transaction`, both throwing to roll

- **`MIGRATION_2_3`** — `DATABASE_VERSION` 2 → 3, registered in `addMigrations`.

Two new tables and their indices. No column added to an existing table, nothing altered, nothing dropped,
**not one row of existing data touched.** The safest shape a migration can have — unlike 7.0's 1 → 2, which
altered two tables and swapped a unique index and still needs a device test.

Built, then compared the hand-written `CREATE` statements against the generated `3.json`:
**every column, both `DEFAULT 0` booleans, both foreign keys with CASCADE, and all three indices (including
the unique `planId + position`) match exactly.** This is a real check — Room refuses to open the database on
any difference, so a mismatch here would have been a crash on the first launch after upgrading.

`3.json` is now in `app/schemas/` alongside `1.json` and `2.json`.

# "Could not build a route" — the optimised route was dead on arrival

**Reported as:** "pa fix ng optimised route tignan ano problema bakit could not build route sya."

## Root cause: the endpoint path had a spurious `/v2/`
`RoutingConfig.optimizationUrl()` returned `BASE_URL + "v2/optimization"`. Verified against the live
service: **`POST /v2/optimization` → 404** (a plain nginx page, not a JSON error), **`POST /optimization`
→ 200**. Directions and matrix really are under `/v2/`, so the path was pattern-matched from them — and
the class note claiming "a wrong path answers 404 rather than 401" had been written from the *directions*
endpoint and never re-checked here. Every optimised route had failed since Phase 8.3 was written.

## Three more real bugs found while verifying, all in the same chain
1. **Totals read from the wrong object.** `OptimizationResponseParser` looked for `summary` inside
   `routes[0]`; VROOM puts it at the **top level** of the response. Both totals were therefore always 0,
   so the screen would have rendered "N stops · 0 m · …". Now reads root summary → route summary →
   route's own `distance`/`duration`, in that order.
2. **No distance unless `"options": {"g": true}` is sent.** The service omits `distance` entirely
   otherwise — only `duration` and `cost`. Measured on the live service with 50 stops: **8,058 bytes
   without it, 13,304 with it** (≈ +5 KB, not the "roughly triples" the original comment claimed). The
   `geometry` it also returns is ignored by the parser; the option is requested for the distance.
3. **Matrix body sent coordinates where the API wants indices.** `sources`/`destinations` must be indices
   into `locations` (`[0]` and `[1..n]`); coordinate pairs answer **400** `"Parameter 'sources' has
   incorrect value or format."`. This failed **silently** — `requestMatrix` returns `null` for any
   non-200, the caller reads that as "no answer" and falls back to straight-line distance. So Phase 8.2's
   whole point (real road distance) was never once exercised; the fallback was the only path ever taken.

## Also improved
- Non-200 failures now carry the **service's own message** (read from `getErrorStream()`, capped at 160
  chars). A 500 from the optimization endpoint means the solver found **no road near one of the
  coordinates** and the message names which one — that is the difference between "try again" and "move
  that pin". Previously every distinct failure read "HTTP 500".
- `OptimizedRouteFragment` appended `\n\n()` when the detail was empty (NOT_CONFIGURED,
  TOO_MANY_STOPS, QUOTA_EXHAUSTED). Now appended only when there is something to say.

# The route order moved onto the device — the service is no longer called

**Reported as:** "manual nalang sa plan route paiba lahat ayaw kase gumana hayst basta sya na maglagay ng
sunod sunod pagkaka sunod sunod ng route ganun"

## What was built
`domain/RouteOrderPlanner` (PURE, 23 tests) — two steps:
1. **Nearest neighbour** from the current position (falling back to Home, then the lowest id). Ties go to
   the lower id, and the input is sorted by id first, so the same stores always give the same route.
2. **2-opt refinement** — sweep the route for any stretch that reads better backwards and reverse it.

`RoutingRepository.planRoute()` runs it in-process (main thread; ~2,500 distance calculations for 50
stores). `OptimizedRouteFragment` calls that instead of `optimize()`. The screen can no longer fail on a
network, key or quota problem, and VROOM's 50-stop cap no longer applies.

ordering and it is verified working, so going back is one line in the fragment.

## Measured, not asserted — the numbers that justified 2-opt

from the matrix endpoint (the planner itself only ever sees straight lines):

| approach | six fixtures | vs VROOM |
|---|---|---|
| nearest neighbour alone | 249.2 km | **+12.5%** |
| nearest neighbour + 2-opt | 225.3 km | **+1.8%** |
| VROOM | 221.4 km | baseline |

2-opt closed almost the whole gap and **beat VROOM on 3 of the 6 fixtures**. Raw greedy would have been a
route that looks sensible and costs a fifth more driving.

## The bug the tests caught

place. Fix: null reference → **0** (edge invisible, reversal judged on the measurable edges), NaN
coordinate → **infinity** (never accepted). A test (`theRefinementKeepsAnUnusableCoordinateAtTheEnd`) pins it.

# ✅ MAY STORE PALA — so it WAS a real bug. The Round panel never worked.

The user answered: **"oum may store na nga."** So the stores exist and the panel still said 0 of 0.

## Root cause: the FOURTH instance of the `LiveData.getValue()` trap
`SettingsFragment.refreshRound()` read:
```java
app.settingsRepository().observe().getValue()
app.storeRepository().observeAll().getValue()
app.completionRepository().observeAllOrdered().getValue()
```
while `observeRound()` observed **different objects**:
```java
app.storeRepository().observeAll().observe(...)
```

**Room generates every `LiveData`-returning DAO method as
`getInvalidationTracker().createLiveData(...)` — a NEW LiveData on every call.** Verified in
`app/build/generated/.../StoreDao_Impl.java:395` (and `AppSettingDao_Impl:116`,
`CompletionHistoryDao_Impl:70`).

So the instances being *read* had never been *observed*. `getValue()` was `null` every time →
`RoundCalculator.compute(null, null, 1)` → `RoundProgress(1, 0, 0)` → the panel read
**"Round 1 in progress · 0 of 0 stores visited"** with **"Start next round" permanently disabled** —
for ever, with any number of stores. Exactly the screenshot.

## The fix
Capture each LiveData **once** into a field, then observe *and* read that same field:
```java
roundSettings = app.settingsRepository().observe();
roundStores   = app.storeRepository().observeAll();
roundHistory  = app.completionRepository().observeAllOrdered();
```
plus a guard that all three have arrived before drawing — because a partial answer renders "0 of 0" on a
screen that has stores, which is the wrong number this whole bug was about.

## Why the identical-looking reads elsewhere are fine
`LocationProvider.currentFix()` **returns a field**, so it is a stable instance — which is why
`MapFragment`, `RoutePreviewBottomSheet`, `HomeSetupFragment` and `StoreDetailBottomSheet` reading
`.getValue()` on it are all correct. **Check which shape an accessor is before trusting `getValue()`.**
Grepped the whole `ui/` tree for `accessor().getValue()`: the Settings round panel was the only broken one.

Earlier I said the Dashboard's `card_dashboard_empty` was dead UI. **Wrong** — it is wired as `emptyCard`

# Version 19 — MANUAL two-way cloud sync (Save to cloud / Retrieve from cloud)

**Requested as:** "ma save tapos kapag two way pero lagyan mo ng mga safety feature lagayan mo ng save to
cloud at retrieve from cloud para controlado pa ren"

So: **two-way, but manual** — two explicit buttons, not a background transport. That is a better design

## The key insight that made this small and safe
**A cloud save IS a backup, and a cloud retrieve IS a restore.** So:
- **Push** = `BackupRepository.buildBackupText()` → one Firestore document. There is no second definition
  of "the app's data" to drift from the file export.
- **Pull** = read the document → `BackupCodec.parse` → `BackupValidator.validate` → **the same**
  `BackupTransactionDao.importAll` the file import uses. Validation, merge rule, single transaction and
  rollback are all the ones that already existed and were already tested.

Writing a second import path for the cloud would have meant a second set of rules free to disagree with the
first — and the one that ran last would win. **Reusing the tested path IS the safety feature.**

## What was built
- **`domain/CloudSyncSummary`** (PURE, 13 tests) — what a merge *would* add, before it happens. Mirrors
  `importAll`'s merge rule exactly: a store already here by **store code** is kept (the app's copy wins), a
  completion already here by **(storeCode, round)** is skipped, and a completion naming a store in neither
  place is reported **unresolved** rather than dropped. The preview is a promise; if it lied, the
  confirmation dialog would be decoration.
- **`data/sync/CloudSyncRepository`** — `refreshStatus` / `saveToCloud` / `fetchFromCloud` / `applyFromCloud`.
  Document at `users/{uid}/cloud/backup`, holding `json` (the whole backup) plus readable `storeCount`,
  `completionCount`, `exportedAt`, `updatedAt`, `deviceLabel` so the console shows something meaningful.
  `documentForSignedInUser()` reads the uid **fresh every call** — a cached uid would put one person's round
  into another person's cloud after a sign-out/sign-in.
- **Settings → Cloud card**: status line + Save to cloud + Retrieve from cloud + a progress bar.

## Safety features, complete list
sign-in required · push never deletes locally · an EMPTY database is refused rather than replacing a good
cloud copy with nothing · **retrieve previews counts before writing** · **merge is the default, replace is a
separate button behind a second confirmation** · one operation at a time (both buttons die while in flight)

The `SyncManager` seam is still `NoOpSyncManager`, and that is now a **decision, not a gap**: a transport

`btn_store_save` · `btn_place_link_continue` · `btn_nav_confirm` · `btn_nav_open_maps` ·
`btn_route_preview_start`

They all *work*; they just do not look like buttons. That is why nobody noticed for several versions, and
it is exactly the "flat, unfinished" feeling the user was describing. **All five now name their style**,
and `styles.xml` carries the full explanation so the next sheet does not repeat it.

**Lesson: when a screenshot looks wrong, read the library rather than guessing at the theme.** The AAR is
on disk and the answer took one extraction.

## Fixed in the Settings screen
1. **"Save to cloud" wrapped onto two lines.** Both buttons were content-sized in a `gravity="end"` row;
   the two labels plus padding need more than the ~312dp a 360dp screen gives. Fixed three ways at once,
   because any one alone leaves it reachable: **`layout_weight="1"`** on both, **one-word labels**
   ("Save" / "Retrieve"), and **an icon each** to carry the dropped word. `maxLines="1"` as the backstop.
2. **The account card printed the email twice.** `AuthUser.label()` falls back to the email when there is
   no display name, and the card drew both lines. Now the heading shows the label and the second line is
   suppressed when it would repeat — two identical lines read as a rendering bug, not a missing name.

## Store Details sheet, rebuilt
The five fields were a stack of label-above-value pairs — a small grey caption, a line of value, 12dp, the
next caption. Five fields came to about half a screen of very sparse text. Now a **key-value list**: label
left, value right, hairline dividers. Same five facts in about half the height, and the eye scans one
column of values instead of hunting for where each one starts. The label column has `minWidth="104dp"` so
the values line up. Status chip moved onto the title row. Button hierarchy is now explicit:
**Get directions** filled, **Store completed?** tonal, **Edit/Delete/Close** text.

## A mistake I made
